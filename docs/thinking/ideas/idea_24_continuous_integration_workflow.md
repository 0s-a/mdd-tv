## 1. التوصيف العام والدافع (Overview & Motivation)

### 1.1 ملخص الفكرة
إنشاء خط أنابيب سحابي خفيف وسريع للفحص المستمر (`.github/workflows/ci.yml`) ينشط تلقائياً عند دفع أي تحديث برمجى (`push`) أو فتح طلب سحب (`pull_request`) على الفروع التطويرية والفرع الرئيسي `main`. يقوم الخط بتشغيل أمرين أساسيين حصراً:
1. فحص تجميع كود كوتلن بنجاح عبر `./gradlew compileDebugKotlin`.
2. تشغيل اختبارات الوحدة الصامتة عبر `./gradlew testDebugUnitTest`.

يتم استبعاد بناء حزم الإنتاج الكاملة (`assembleRelease`) في هذا الخط لتوفير دقائق الحوسبة السحابية وحصر التوليد النهائي عند إطلاق الـ Tags فقط في `release.yml`.

### 1.2 الدافع ومبررات الإضافة
* **الحماية المبكرة للفرع الرئيسي:** منع دمج أي كود مكسور تجميعياً أو يحوي تعارضات ناتجة عن تعديل ملفات متعددة بالتوازي.
* **التحقق المستمر من عقود MVI:** التأكد من أن التعديلات في طبقتي Domain و Presentation لا تكسر كائنات الحالة `UIState` أو اختبارات الـ ViewModels.
* **إلغاء الاعتماد على الفحص اليدوي:** توفير بيئة فحص محايدة ونظيفة ومطابقة للإنتاج على خوادم GitHub Actions.

## 3. فحص التعارضات المعمارية والبرمجية (Architectural Conflicts Audit)

### 3.1 التعارضات مع موارد بيئة العمل والحوسبة
* **استهلاك دقائق الحوسبة المجانية على GitHub Actions:**
  * *المعالجة:* تفعيل كاش Gradle التلقائي عبر `gradle/actions/setup-gradle@v4` لتخزين التبعيات والمخرجات، وقصر الفحص على `compileDebugKotlin` مما يقلص زمن التشغيل إلى أقل من دقيقتين.
* **تعطل الـ CI في غياب السيرفر الحي:**
  * *المعالجة:* اختبارات الوحدة في `testDebugUnitTest` معزولة تماماً (Hermetic Unit Tests) وتستخدم بيانات وهمية (Mock Data) دون الاعتماد على خادم Jellyfin الحي.

## 4. المخرجات الهندسية ومخطط التنفيذ (Engineering Deliverables)

* إنشاء ملف خط العمل: `.github/workflows/ci.yml`.
* قصر المشغلات على:
  ```yaml
  on:
    push:
      branches: [ main, 'feature/**', 'fix/**' ]
    pull_request:
      branches: [ main ]
  ```
